# 密钥与环境变量运维手册

**相关脚本**：`scripts/installer/bootstrap.sh` → `python -m installer`（步骤 `[4/7] 初始化 .env`；2026-10-04 起旧 install.sh 已删除）
**最近验证**：2026-09-10 @ 192.168.10.10（Ubuntu 24.04 / 纯测试机）
**关联文档**：`运维手册-备份与恢复.md`

---

## 一、密钥清单

| 变量 | 用途 | 缺失后果 | 轮换影响 |
|------|------|---------|---------|
| `SECRET_KEY` | Flask session 签名 | `FLASK_ENV=production` 时拒绝启动 | 所有用户被登出 |
| `JWT_SECRET_KEY` | JWT 签发/校验 | 同上 | 所有 token 立即失效 |
| `SWITCH_SECRET_KEY` | AES-256-GCM **数据加密密钥** | 拒绝启动（`config.py:692`） | ⚠️ **受密文约束**，见第四节 |

三者均为 **64 字符 hex（32 字节）**。定义位置：`config.py:341`。

---

## 二、自动注入机制（安装器 [4/7]）

每次运行安装器（`python -m installer`）都会执行一次**幂等**的密钥注入：

| `.env` 现状 | 脚本动作 |
|------------|---------|
| 键已存在、值正常 | **不动** |
| 键已存在、值为空 | 生成随机值覆盖 |
| 键已存在、值为 `change-me*` 占位符 | 生成随机值覆盖 |
| **键整行不存在** | **新增该行并生成随机值** |

注入完成后脚本立即 `set -a; . .env; set +a` 加载到当前进程。

> 设计意图：生产配置对空值/占位符会直接拒绝启动，脚本提前修复，避免部署者漏填。

## 三、缺陷记录（2026-09-10）

### 3.1 「只修不增」导致新密钥永远补不上（已修复）

**现象**：`.env.example` 中已新增 `SWITCH_SECRET_KEY`，但装机后 `.env` 里始终没有该键，直到 `FLASK_ENV=production` 启动 `ipip-monitor` 时才以「启动即崩、被 systemd 反复拉起后 failed」的形式暴露。

**根因**：原实现只遍历 `.env` 的**已有行**，键整行不存在时直接 `continue`，永不新增：

```python
for i, line in enumerate(lines):
    if not m or m.group(1) not in targets:
        continue          # ← 键不存在 → 直接跳过，不会新增
    if val == "" or val.lower().startswith("change-me"):
        lines[i] = ...    # ← 只修改"已存在的行"
```

而 `.env` 来自 `cp .env.example .env`，该步**仅在 `.env` 不存在时执行** → 模板后续新增的键不会回流到已存在的 `.env`。

**修复**：遍历结束后补齐 `targets - present` 的缺失键：

```python
for key in sorted(targets - present):
    lines.append(f"{key}={secrets.token_hex(32)}")
    generated.append(key + "(新增)")
```

**验证结果**：

| 场景 | 结果 |
|------|------|
| 删掉该行后重跑 | `已自动生成随机密钥: SWITCH_SECRET_KEY(新增)` ✅ |
| 紧接再跑一次（幂等） | `SECRET_KEY / JWT_SECRET_KEY / SWITCH_SECRET_KEY 已配置，跳过`，键仍 1 行、值不变 ✅ |
| 全量键差异比对 | `.env` 与模板无其它缺失键（0 个）✅ |

### 3.2 遗留边界：非密钥类新增变量不会自动同步

注入只覆盖上述 **3 个密钥键**。模板里其它新增变量（功能开关、超时配置等）对已存在的 `.env` **不会生效**，需手工同步。比对命令：

```bash
cd /root/ipip-deploy
python3 - <<'PY'
import re
def keys(p):
    return {m.group(1) for m in
            (re.match(r"^([A-Za-z_][A-Za-z0-9_]*)=(.*)$", l) for l in open(p, encoding="utf-8")) if m}
env, ex = keys(".env"), keys(".env.example")
print("模板有而 .env 缺失:", sorted(ex - env) or "无")
PY
```

## 三·补 缺陷记录（2026-10-05）：安装器生成的 `SWITCH_SECRET_KEY` **根本无法使用**

> 严重度：**高** —— 影响所有用安装器全新安装的机器，且是**静默**的（装机不报错，
> 要到有人真的去加一条设备凭据才暴露）。

### 现象

测试机「SNMPv3 添加凭据」报服务器内部错误。`error.log` 根因：

```
加密失败: SWITCH_SECRET_KEY 格式无效：… 当前长度: 64
```

### 根因（结构性，不是某台机器配错）

同一段生成代码给**三类约束完全不同**的密钥用了同一把随机串：

| 环节 | 事实 |
|---|---|
| 生成 | `envfile.py` 统一用 `secrets.token_urlsafe(48)` |
| 产出 | 恒为 **64 字符**（实测 1000 次全部如此），URL-safe base64 解码 = **48 字节** |
| 消费 | `encryption.py` 的 AES-256-GCM 要 **恰好 32 字节** |

⇒ 生成的值**永远不可能**被接受。表现就是：全新装好的机器上，
设备凭据加解密功能从第一天起就是坏的。

**为什么会长期潜伏**：`tests/scripts/test_installer_production_check.py`
的造数函数**也用了 `token_urlsafe(48)`** —— 测试与实现同源，两边一起错时
断言永远成立（同义反复）；而加密侧的门禁一律用 `"ab" * 32`（64 字符纯 hex）
造密钥，走的是另一条分支。**两套测试各自自洽，合起来漏掉整条端到端链路。**

### 修复

1. **生成侧**（`envfile.py`）：按密钥类型分派生成器。`SWITCH_SECRET_KEY`
   用 `secrets.token_hex(32)`（64 字符纯 hex = 32 字节）；会话类密钥
   （`SECRET_KEY`/`JWT_SECRET_KEY`）**保持原样不动** —— 它们无长度约束，
   改了会换掉存量机器正在用的值 ⇒ 一次静默的全站登出。
2. **消费侧**（`encryption.py`）：base64 解码同时容忍标准表与 URL-safe 表
   （`token_urlsafe` 的产物含 `-`/`_`，只用标准表会报 "Incorrect padding" ——
   报的是填充、真因是字符集，又是一个会把人带偏的错位提示）。
3. **顺带修**：`generate_missing_keys()` 缺 `return`，恒返回 `None`
   （docstring 与签名都写着返回列表）。原先无人接返回值所以没暴露 ——
   **契约说谎**。

### 为什么本手册第一节早就是对的

第一节写「三者均为 **64 字符 hex（32 字节）**」。**文档是对的，代码是错的。**
这次是把实现对齐到文档，不是反过来。

### 加固（防止再犯）

新增 `tests/scripts/test_installer_key_shape_e2e.py`，直接钉**端到端链路**：

- **用生成器真的生成 → 喂给真的 `encrypt()`/`decrypt()`**（原来缺的就是这一段）；
- 生成值解码后**必须恰好 32 字节**（断言字节数而非字符数 —— 混为一谈正是
  本次事故的误导来源）；
- 显式登记"历史形状（`token_urlsafe(48)`）必须被拒绝"作为反例；
- URL-safe 字母表的 32 字节密钥必须能用（含 `-`/`_` 时）；
- 会话类密钥**不得**被改成专属生成器（防"顺手统一"造成静默轮换）。

同时把 `test_installer_production_check.py` 的造数函数按用途拆开，
消除"测试与实现同源"的同义反复。

### 存量机器怎么办

- **已按安装器生成、且尚未写入任何密文**的机器：备份 `.env` 后
  `sed -i` 换成 `python -c "import secrets;print(secrets.token_hex(32))"`，
  重启服务即可（本次测试机就是这么处理的）。
- **已有密文**的机器：**不能直接换** —— 先按第四节做密文迁移。
- **怎么确认有没有密文**：
  ```sql
  SELECT COUNT(*) FROM switch_credentials WHERE password IS NOT NULL AND password <> '';
  SELECT COUNT(*) FROM monitor_credentials;
  ```
  两处都是 0 ⇒ 无存量密文，可放心换。

## 四、⚠️ `SWITCH_SECRET_KEY` 轮换（有密文约束）

### 4.1 它保护什么

| 密文位置 | 内容 | 直接换钥的后果 |
|---------|------|--------------|
| MySQL `switch_credentials` 表 | 交换机登录凭据 | **永久无法解密**，需重新录入设备凭据 |
| **Redis** 快照 `api_key_enc` | AI API Key | AI Key 失效，需在界面重填（若 `AI_API_KEY` 由 env 提供则不受影响） |

- 加密实现：`app/utils/security/encryption.py`（AES-256-GCM，密钥支持 hex/base64）
- 落库迁移先例：`migrations/run_phase3_4.py`

### 4.2 轮换前置检查（必做）

```bash
cd /root/ipip-deploy
for t in switch_credentials ip_switch_info device_switch_ext switch_port_ips; do
  printf "  %-22s " "$t"
  mysql -uipip -p"$MYSQL_PASSWORD" ip_management -N -e "SELECT COUNT(*) FROM $t;"
done
```

- **全部为 0** → 可直接轮换（无密文，无损失）
- **任一非 0** → **禁止直接替换**，必须先迁移密文

### 4.3 正确轮换流程

1. **停机窗口**：`systemctl stop ipip-web ipip-monitor ipip-gateway ipip-celery-ai ipip-celery-voice`
2. **备份**：`.env` + 数据库（见 `运维手册-备份与恢复.md`）
3. **迁移密文**：旧密钥解密 → 新密钥加密。迁移脚本须沿用 `app/utils/security/encryption.py` 的算法与密钥派生方式（**勿照搬** `run_phase3_4.py` 里的 `key.encode()[:32].ljust(32, b'\0')` 截断式派生，与 runtime 实现不一致）
4. **更新 `.env`** 的 `SWITCH_SECRET_KEY`
5. **启服务并验证**：`GET /api/health/check` = 200；抽查一条设备凭据可正常解密

### 4.4 反面案例（2026-09-10 实测踩到）

为验证「缺键补齐」，直接 `sed -i '/^SWITCH_SECRET_KEY=/d' .env` 再跑脚本 → 脚本按预期生成了**新密钥**，但旧密钥从此丢失（`874c8a06…` → `a9c90f0c…`）。

本次因上表 4 张相关表**均为 0 行**，无实际损失。但该操作等同于一次**无迁移的密钥轮换**，若库中已有真实凭据，将直接造成数据不可用。

> **教训**：验证密钥注入逻辑，请使用**新建的临时 `.env`** 做实验，绝不要在真实 `.env` 上删键。

## 五、灾难恢复盲区：备份不含 `.env`

`backup_system.py` 的产物**只含 MySQL dump + `instance/` 数据面，不含 `.env`**。

因此服务器整机损毁后：

- 数据库可以恢复 ✅
- 若 `SWITCH_SECRET_KEY` 同时丢失 → `switch_credentials` 中的密文**永久不可解** ❌

**要求**：`.env` 必须**离线单独留存**（密码管理器 / 密钥保管渠道），并纳入变更管理；含密钥的 `.env` 不得进入代码仓库。

## 六、常见问题

**Q：安装后 `ipip-monitor` 反复重启并进入 `failed`？**
A：检查 `SWITCH_SECRET_KEY` 是否为空。`FLASK_ENV=production` 时 `config.py:692` 强制校验，缺失即拒绝启动。修复：重跑 `bash scripts/installer/bootstrap.sh`（[4/7] 会自动补齐）或手工补该键后重启服务。

**Q：`.env.example` 里加了新变量，部署后没生效？**
A：见 3.2，非密钥键不会自动同步，需手工追加。

**Q：安装期依赖类报错（pnpm / Node 版本 / starlette 冲突）？**
A：见 `IPIP功能缺口评审报告-部署仓库视角.md` 的缺陷清单。

## 七、凭据重置（admin / MySQL / 应用密钥）

安装收尾时安装器会**统一展示一次凭据清单**（含 `.env` 里的明文密码与管理员
账户状态），并指出留档位置。日常重置改用 `scripts/credentials.py` —— 它与
`migrations/seed_users.py` 的分工是：后者负责**首次创建**（bootstrap），前者负责
**运维期重置**。

```bash
python scripts/credentials.py show                      # 查看凭据清单 + 管理员状态
python scripts/credentials.py reset-admin               # 重置管理员密码（默认随机 16 位）
sudo python scripts/credentials.py reset-mysql          # 重置 MySQL 密码并**同步 .env**
python scripts/credentials.py reset-secret-keys --yes   # 重置 SECRET_KEY / JWT_SECRET_KEY
```

### 为什么 MySQL 密码必须「一起改」

`MYSQL_PASSWORD` 同时存在于两处 —— `.env` 里，以及应用所连的 MySQL 账号本身。
只改一处的结果要么「改完就连不上库」，要么「库改了、`.env` 忘了」。`reset-mysql` 会
按顺序完成：改 MySQL 账号 → 原子更新 `.env` → **用新密码当场验证连接** → 提示重启服务。

优先走 root 的 unix socket 连接（Debian/Ubuntu 默认 `auth_socket` 认证，**不需要 root
密码**，但要求 `sudo`）；socket 不可用时回退到 `.env` 中的账号执行 `ALTER USER`。

### 留档与权限

生成的密码打印到 stdout，并追加写入 `$PROJECT_ROOT/.credentials`（权限 **600**，已加入
`.gitignore`）。该文件含历次明文凭据，仅 root 可读——请勿随备份一起流出（见第五节）。

### 两个已知陷阱（均已修复，记录备查）

1. **密码含 `@` 会破坏 SQLAlchemy URI**：`config.py` 拼接 URI 时未做 URL 编码，密码里的
   `@` 被解析成 `user@host` 分隔符 → 主机名变成 `@localhost`，服务启动即 503
   （`Can't connect to MySQL server on '@localhost'`）。现对 user/password 做 `quote_plus`，
   同时生成端不再产出 URI/shell 元字符。
2. **密码含 `$` 会破坏 `source .env`**：旧 `install.sh` 与 `migrations/seed_all.sh` 曾用
   `set -a; . .env` 加载配置，值里的 `$` 被 shell 当真展开，`set -u` 下报
   `unbound variable` 并中断安装。现改用 python-dotenv 解析 + `shlex.quote` 后再 `eval`
   （与 `scripts/dev-start.sh` 同一做法）。

### 不支持重置的项

`SWITCH_SECRET_KEY` **不提供重置入口** —— 它是 AES-256-GCM 设备凭据加密密钥，直接更换
会让既有密文永久不可解，必须走「先用旧钥解密、再用新钥加密」的迁移（见第四节）。
