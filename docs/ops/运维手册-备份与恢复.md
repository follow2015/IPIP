# 备份与恢复运维手册

**工具**：`scripts/backup_system.py` / `scripts/restore_system.py`
**演练日期**：2026-09-10
**演练环境**：192.168.10.10（Ubuntu 24.04.1 LTS / MySQL 8.0.46 / 10 核 / 9.7G / 49G）
**关联文档**：`运维手册-密钥与环境变量.md`

## 一、日常用法

### 备份

```bash
cd /root/ipip-deploy
.venv/bin/python scripts/backup_system.py --output-dir /var/backups/ipip --prune
```

| 参数 | 说明 |
|------|------|
| `--output-dir` | 备份根目录，默认 `backups/system`。**建议与项目不同盘** |
| `--prune` | 备份后按 日7/周4/月3 清理过期备份 |
| `--dry-run` | 只打印将执行的操作，不落盘 |
| `--include-secrets` | 额外把 `.env` 中的密钥 GPG 加密导出为 `secrets.env.gpg`（需 `GPG_PASSPHRASE`） |

> `ipip-backup.service` 已**默认带 `--include-secrets`**（2026-09-14 起），故线上每日备份
> 产物均含密钥文件。手工执行时可省略该参数（则产物不含密钥）。

产物结构（每次一个自包含目录）：

```
ipip-backup-YYYYmmdd-HHMMSS/
  mysql.sql.gz      # mysqldump 全量（--single-transaction --routines --triggers --events）
  dataface.tar.gz   # instance/ 数据面（chroma 向量库 / FTS5 sqlite / pickle）
  secrets.env.gpg   # 仅 --include-secrets 时产出：.env 密钥的 AES256 对称密文
  manifest.json     # sha256 校验清单 + git commit + mysqldump 版本
```

### 恢复

```bash
cd /root/ipip-deploy
.venv/bin/python scripts/restore_system.py --from /var/backups/ipip/ipip-backup-20260910-022209
.venv/bin/python scripts/restore_system.py --from <DIR> --database test_ip_management  # 恢复到指定库
.venv/bin/python scripts/restore_system.py --from <DIR> --skip-mysql                   # 仅还原数据面
```

⚠️ **破坏性**：MySQL 侧会覆盖同名库（dump 含 `DROP TABLE IF EXISTS`）。执行前必须先完成 manifest 校验，脚本默认要求交互输入 `yes`（`--yes` 可跳过，用于脚本化）。

### 调度

`deploy/systemd/ipip-backup.{service,timer}`：每日 03:10 触发，`Persistent=true` 保证关机错过后开机补跑。
默认每日一次 → **最坏 RPO = 24 小时**；需要更小 RPO 请缩短 timer 间隔。

⚠️ 该单元带 `--include-secrets`，因此**依赖 `/etc/ipip/ipip.env` 里的 `GPG_PASSPHRASE`**：
口令缺失或为空时整次备份会**直接失败**（有意为之，避免产生「以为备了」的假象）。
`install-units.sh` 新建 ipip.env 时会自动生成并打印一次；**既有部署升级后请手工补写**，
否则凌晨的备份会静默变成 failed（watchdog 会告警）。详见第四节。

## 二、真实恢复演练记录（T1.8，2026-09-10）

> 演练方式不是模拟脚本，而是**真实 `DROP DATABASE` 后完整还原**。

| 步骤 | 命令/动作 | 结果 |
|------|----------|------|
| 1. 基线 | 记录 `ip_management` 表数与行数 | **72 张表**；monitor_metric_templates=239、monitor_metric_template_group_items=193、component_templates=162、monitor_oid_category_rules=159、role_permissions=112 |
| 2. 备份 | `backup_system.py --output-dir /var/backups/ipip` | 耗时 **0s**，产物 52K（mysql.sql.gz 44503 bytes）；`instance/` 不存在故跳过数据面 |
| 3. 破坏 | `DROP DATABASE ip_management; CREATE DATABASE ...` | 表数 **0** |
| 4. 恢复 | `restore_system.py --from <bkp> --yes` | 耗时 **28s（RTO）**，表数恢复为 **72** |
| 5. 一致性 | 逐项比对上述 5 张表行数 | **完全一致**（239/193/162/159/112） |
| 6. 应用层 | `GET /api/health/check` | **HTTP 200**，database/redis/disk 全 healthy |

**结论**：备份/恢复链路在真实 MySQL 上跑通，数据零丢失（本次演练窗口内无写入）。

**RTO** = 28s（数据量小；实际随库容量增长）
**RPO** = 依赖调度频率，按默认每日 back up 最坏 24h

### 演练暴露的脚本缺陷（已修复）

`restore_system.py` 原用 `subprocess.run(..., stdin=gzip_file)`：
subprocess 会取 `GzipFile.fileno()`，得到的是**底层未解压文件**的 fd，mysql 因此读到 .gz 二进制并报
`ASCII '\0' appeared in the statement`。已改为 `Popen` + `shutil.copyfileobj` 流式喂给 stdin。

> 说明：这个缺陷在本地单元测试中完全测不到——单测只覆盖了 gzip 往返读写，没有真实 mysql 还原路径。
> **备份工具必须用真实数据库演练一次，否则"能备份"与"能恢复"是两件事。**

## 三、注意事项

1. **目标库必须已存在**：mysqldump 产物不含 `CREATE DATABASE`。库被 drop 后需先建空库再恢复。
2. **脚本不依赖 Flask app 上下文**：只用 subprocess + os.environ，避免应用自身故障时恢复工具也失效。
3. **不复用 `app.config["SQLALCHEMY_DATABASE_URI"]`**：该值是 `@property`（`config.py:459-472`），经 `from_object` 拷入的是描述符对象而非字符串。脚本直接读 `MYSQL_*` 裸环境变量。
4. **密码安全**：经临时 `defaults-extra-file`（权限 0600）传入，不出现在 `ps` 命令行；备份产物**不含 `.env`**。
   ⚠️ 由此产生一个**灾备盲区**：整机损毁后数据库可恢复，但若 `SWITCH_SECRET_KEY` 一同丢失，`switch_credentials` 中的密文将**永久不可解**。
   **2026-09-14 起该盲区已收敛**：备份单元带 `--include-secrets`，密钥随产物以 `secrets.env.gpg` 留档，`.env` 不再需要单独留存 —— 但解密口令 `GPG_PASSPHRASE` 本身**必须离线另存**（见第四节）。
5. **`instance/` 数据面**：首次部署尚不存在 `instance/` 时脚本会跳过打包（本次即如此）。一旦启用 RAG，务必验证 `dataface.tar.gz` 已产出。
6. **异地留存**尚未实现，纳入后续计划（加密已随 `--include-secrets` 落地）。

## 四、密钥备份与 GPG 口令（2026-09-14 新增）

### 4.1 为什么有这一节

备份产物**有意不含 `.env`**（避免密钥随备份扩散）。代价是：整机损毁后数据库能恢复，
但 `SWITCH_SECRET_KEY` 一旦丢失，`switch_credentials` 里的设备口令密文就**永久不可解**。

因此 `backup_system.py` 提供 `--include-secrets`：把 `.env` 中的密钥清单（`SECRET_KEYS`）
用 gpg **AES256 对称加密**导出为 `<备份目录>/secrets.env.gpg`。`ipip-backup.service`
**默认启用该项**。

### 4.2 口令放在哪

| 位置 | 说明 |
|------|------|
| `/etc/ipip/ipip.env` 的 `GPG_PASSPHRASE` | 单元经 systemd `EnvironmentFile` 读取；本文件含密钥，权限须 **0600** |
| 你的密码管理器 / 纸质保险柜 | **唯一可靠的一份**——机器没了它必须还在 |

⚠️ **口令不随备份产物分发。** 它丢了，所有 `secrets.env.gpg` 都解不开，等价于「备份没做」。
`install-units.sh` 新建 ipip.env 时会自动生成并打印一次；**既有部署请手工补写**：

```bash
GP=$(openssl rand -base64 48 | tr -d '\n')
grep -q '^GPG_PASSPHRASE=' /etc/ipip/ipip.env \
  && sed -i "s|^GPG_PASSPHRASE=.*|GPG_PASSPHRASE=${GP}|" /etc/ipip/ipip.env \
  || printf 'GPG_PASSPHRASE=%s\n' "${GP}" >> /etc/ipip/ipip.env
chmod 600 /etc/ipip/ipip.env
echo "请立即离线保存: ${GP}"
```

### 4.3 恢复密钥

```bash
gpg --batch --pinentry-mode loopback --passphrase "$GPG_PASSPHRASE" \
    -d /var/backups/ipip/ipip-backup-YYYYmmdd-HHMMSS/secrets.env.gpg
```

输出是可直接 `source` 的 `KEY=value` 行。备份脚本自身只打印**键名**，值绝不落日志。

### 4.4 两个实现细节（排障用）

- **`GNUPGHOME=/run/ipip-backup-gnupg`（配 `RuntimeDirectory=`）**：单元内 `ProtectHome=true`
  会把 `$HOME` 换成空目录；更关键的是 —— **gpg 不会自己创建 `GNUPGHOME`**：目录不存在时直接报
  `keyblock resource '.../pubring.kbx': No such file or directory`，并让**整次备份失败**。
  2026-09-14 真机实测排除了误判：`/tmp` 与 `/run` 在单元命名空间里**都可写**，唯独「缺目录本身」
  才是根因。故用 `RuntimeDirectory=ipip-backup-gnupg` + `RuntimeDirectoryMode=0700` 让 systemd
  预建该目录；它位于 `/run`，在 `ProtectSystem=strict` 下仍可写，且随单元结束自动清理，
  顺带避免 gpg-agent socket 残留导致的挂起（见 `backup_system.py` 的 `GPG_TIMEOUT_S`）。
- **空口令 = 硬失败**：空口令下 gpg 仍会「成功」产出一个谁都能解开的文件，那是虚假的安全感，
  故脚本直接 `RuntimeError`，且失败会让整次备份不落 manifest。
